## Premise

A trading platform loses three kinds of thing for good, and everything else it
computes can be computed again.

1. **Captured market data.** A quote not recorded when it existed is gone. A
   vendor's history is no substitute, because vendors restate history after
   the fact. The sibling
   [quantitative-trading](https://github.com/l3a0/quantitative-trading)
   repository measured that drift: an adjusted close is a function of the day
   it was downloaded.
2. **The order and fill record.** It is the audit trail, the input that
   calibrates the transaction cost model, and the only way to reconcile what
   the platform thinks it holds against what the broker says it holds. A fill
   nobody journaled cannot be reconstructed from the platform's own state.
3. **Capital.** A strategy can be re-researched. A loss cannot be undone.

A forecast, a backtest, a target portfolio and a report are all regenerable
from those three. That asymmetry is what the ranking rule in
[CLAUDE.md](../CLAUDE.md) protects. A path that can lose captured data or the
order record is never deferred, and a path that can lose capital sits behind
the hard limits, which no ranking overrides.

## One runtime

What is tested must be what runs live. A backtester written apart from the
live engine is a second implementation of every strategy it runs, and the two
drift without either looking wrong. Narang names backtest software and data
feed handlers among the places model risk lives (L4616 in the
[highlights](https://github.com/l3a0/trading-strategies/blob/main/research/book-notes/inside-the-black-box.md)).

Kleppmann reaches the same conclusion about data pipelines. Keeping one piece
of logic in both a batch system and a streaming system costs significant
effort, and debugging, tuning and maintaining two systems stays costly even
when a library lets one piece of code target both (*Designing
Data-Intensive Applications*, 1st ed., O'Reilly Media, 2017, Kindle location
15718, cited below as DDIA L15718).

So the platform has one set of modules, following the boxes in the charter's
module table, and three adapters at its edges.

1. **The data source**, which replays committed history in a backtest and
   reads a live feed on paper and live.
2. **The clock**, which steps through history in a backtest and follows the
   wall clock otherwise.
3. **The broker**, which is a simulator in a backtest and in shadow running, a
   broker's paper account on paper, and the real account only once the owner
   switches it.

The price is that every module has to be written against an event and clock
interface from its first commit, which is slower than a vectorised backtest
over a price array. What it buys is that a strategy's backtest and its paper
run exercise the same lines of code.

## Design principles

A principle earns a place here only when a design can pass or fail it, which is the test *The Art of Scalability* sets for its own (Abbott and Fisher, 1st ed., Addison-Wesley, 2009, Kindle location 4588, cited below as AoS L4588). A principle like "scales infinitely" fails that test, because no design can be checked against it. Each rule below names the check a review runs, and the reason for it.

The owner's standing directive is to design for 100 times the first load and build for the first load. The book states the same idea as designing every major system so it can be split along at least two axes, while building only the split that today's load needs (AoS L4684, L8205). Its three axes are clones of the whole system (x), a split by function or by kind of data (y), and a split by a key such as account or symbol (z) (AoS L7432).

*Designing Data-Intensive Applications*, cited in [One runtime](#one-runtime), adds the rules for data that the first book leaves out: what to do about faults, clocks, retries, concurrent writers and records that must outlive every bug. A citation like DDIA L9286 is the Kindle location of one of the owner's highlights or of a screen of the book's full text. One like DDIA L\~14160 points into the full text at a location good to about one screen, because the reader shows this book's Kindle pages rather than its locations, so the location of a screen with no highlight on it is interpolated. Where its rules restate one already here, the rule below cites both books rather than appearing twice.

So these rules are checks on a design, and a review applies all of them. A module builds the mechanism a rule names when the path it guards first runs, which the walking skeleton does for the order path, and no sooner. Three kinds of mechanism are built from the first run whatever the count, because CLAUDE.md's ranking rule exempts them.

1. Whatever keeps data that cannot be recaptured from being lost: disk headroom for capture and the journal, capture's place outside every halt, the guard that keeps cleanup rules off recorded data, captured data stored as received with its timestamps, a schema version and a checksum on every recorded record, each journal entry on stable storage before its send, a copy off the machine before the first capture is relied on, and capture's refusal to discard when its buffer fills.
2. Alarms and halts, which read zero while they are healthy, including the clock-offset halt, the lag alarms on the capture buffer and the journal writer, and the scheduled read-back of recorded data.
3. The guards on the order path, whose price is paid by building them late: the sizing rule, the single sender, a lease number in every journal entry and client order id, applying each fill once, the block on unknown orders, and the halt state read just before each send.

### Design ahead, and write down where the build stops

1. **The next scale step exists as a written design, and the only code built ahead of it is configuration.** The book's example is a data-access layer designed so it could reach several databases while one runs. Its migration scripts are written when the need arises, and the design is what lets a second database take weeks rather than months (AoS L1078). Here the only code built ahead is a configuration value, such as a partition count, whose other settings a test runs. A script or path offered later as the next step has run once, in a drill on a copy, before anything relies on it.
2. **Every implementation states its written scale limit, and an alarm or a test trips at 75% of it.** Code built for "any number of read nodes" that handles five has a limit of five (AoS L1174). The limit is stated beside the code that enforces it, and 75% is the headroom ceiling in rule 4. On the order path, reaching the limit halts.
3. **A partition key and a fixed partition count are set from the first commit.** The book finds a split by function "not so easy" to design room for in advance (AoS L7781), so module boundaries and data ownership are settled early. Captured data is keyed by its source, the vendor's identifier as received, and the date it was recorded. The key only routes a record and never identifies it, and a write into a key that already holds data adds a new vintage rather than replacing one. The trading loop is keyed by account. A key maps to a partition through a hash that is the same in every process. DDIA warns that a language's built-in hash can differ from one process to the next, naming Java's and Ruby's (DDIA L6211), and Python's `hash()` on a string does the same. AoS treats the count of a split by key as a number to raise later (AoS L7781). DDIA finds that changing the count moves data, so a database usually fixes it when the data is first laid out and grows by moving whole partitions between machines (DDIA L6411, L6443). Routing by the key modulo the machine count moves most keys whenever a machine is added (DDIA L6418). So the count is fixed at the start, set well above the machine count and chosen for 100 times the first load, and no higher, since each partition carries its own overhead (DDIA L6443).
4. **Plan headroom per component, at 50% of measured capacity and never above 75%.** The measured maximum can be wrong, growth estimates can be wrong, and behaviour near the limit turns erratic (AoS L4449, L4475, L4480). Headroom is computed for each component, never for the system as a whole (AoS L4496). Here that means capture disk, journal volume and the broker's API rate limits. A share of the rate limit is reserved for cancels and the kill switch, and new orders never draw on it.
5. **Every written scale limit names the load parameter it is measured in, and the design names the operations it assumes are common.** DDIA's case is that a scalable architecture rests on assumptions about which operations are common and which are rare, and that a wrong assumption makes the scaling work wasted at best and harmful at worst (DDIA L627). It also finds that a fast-growing service usually rethinks its architecture at each tenfold rise in load (DDIA L598). That finding sits beside the owner's 100x directive rather than against it. A design for 100 times the first load holds only along the parameters it names, so it names them, such as orders per second per account, symbols captured, and messages per second at the open, and a review checks them against measured use. Load along a parameter the design never named is the case that forces a rewrite. Stateful parts stay on one machine until cost or an availability target forces a split, which DDIA reports as the common practice for databases until recently (DDIA L614). The same chapter finds that an early product does better to iterate on its features than to scale for load it may never see (DDIA L621), which is the build-at-1x half of the directive. A written limit holds for the heaviest key, not the average. DDIA's case is a service whose users average about 75 followers while one user's post reaches over 30 million, so the spread of followers per user was the load parameter that mattered (DDIA L464, L473). Here that means the busiest symbol at the open, and the largest partition of any partitioned job, which finishes only when its slowest partition does (DDIA L12589).

### Keep the order path isolated

The **order path** runs from the target portfolio through the risk gate and the journal to the broker adapter. A **synchronous dependency** on it is a call that leaves the process or waits on input or output. A call between modules inside the process, through their shared interfaces, is not one.

1. **Nothing that does not earn money can stall the order path.** The book's first rule of fault isolation is to protect whatever is closest to the money (AoS L7130). Monitoring, reports, dashboards and research reach the order path only asynchronously, and are allowed to fail. The book's own case is a monitoring database whose slowness backed up every user query until the site went down (AoS L8616). The loss stop and the kill switch live in the risk gate and are read on every order, never in monitoring.
2. **Count the synchronous dependencies on the order path and keep them to the minimum.** Availability multiplies along a chain. One hundred parts at 99.999% each give about 99.9% together, which turns about 5 minutes of downtime a year into over 500 (AoS L8698). The minimum here is the input data, the risk gate, the journal and the broker. The journal write is synchronous on purpose, because hard limit 4 puts it before the send.
3. **A fault boundary is drawn around the whole loop, never around a layer, and every crossing is listed.** In the book, a unit isolated from faults shares nothing with its neighbours, takes no calls across its boundary, and carries every transaction from start to finish inside itself (AoS L7088, L7101, L7113). A boundary drawn around all the databases, or all the risk checks, only groups like parts, and one failure there still reaches every transaction (AoS L7117). The book lets one boundary hold one tenant or many (AoS L7147). So the first build is one boundary holding every strategy sleeve, and a split by account comes when load or risk calls for it. Two strategies in one broker account share buying power, so they never sit in different boundaries. Three crossings are allowed, and any other breaks the boundary.
   1. Captured data flows in, read only and one way, and a stale feed halts the sleeves that read it.
   2. Monitoring reads outward only.
   3. The kill switch flows inward to every boundary, and a boundary that cannot read it halts.

### Faults are expected, and the platform checks itself while it runs

1. **Every fault the design says it handles is injected on purpose, in replay.** DDIA separates a fault, one part leaving its specification, from a failure, the whole system no longer serving (DDIA L293). It finds many critical bugs in poor error handling, and recommends causing faults on purpose to keep that handling exercised, and testing even unlikely ones (DDIA L300, L8461). This doc reads "poor" as handling that rarely runs. Here the simulated broker and the replay harness can inject eight faults, and a test runs each through the full loop.
   1. An acknowledgment that never arrives, and one that arrives late.
   2. A fill delivered twice, a fill that arrives after a cancel was acknowledged, and a fill the broker later corrects or busts.
   3. A process killed between the journal write and the send, and killed in the middle of a journal write.
   4. A process paused between an accepted journal write and its send.
   5. A clock that jumps forward or back, and a time service that stops answering.
   6. A feed that stops, and a feed that repeats messages.
   7. A journal that cannot be read, which the owner's procedure for orders in doubt resolves from the broker's records alone (DDIA L11110, L11139).
   8. A standby or a derived view that lags by minutes to hours (DDIA L5126).
2. **A guarantee the platform relies on is checked while it runs, and a mismatch halts.** DDIA's example is a queue that compares messages in with messages out and alerts on any gap (DDIA L372). Faults that share a cause across parts produce more failures than independent hardware faults, and the bugs behind them wait for the day an assumption stops holding (DDIA L351, L366). So the checks run on every fill and at a set interval, not only at the end of the day: the journal's orders against the broker's, fills against positions, and the vendor's sequence numbers against what capture recorded. A check reads both sides at one consistent point, since a check that sees two moments reports a gap that is only timing, and a platform that halts on its own timing learns to ignore the alarm (DDIA L7218, L7227). Queries to the broker draw on the general share of its rate limit, never on the share reserved for cancels.
3. **Every recorded record carries a checksum, and every read verifies it.** The checksums built into network protocols catch corruption on the wire, but not a bug at either end or corruption on disk, so DDIA calls for checksums from end to end (DDIA L16445, L9376). A crash can also leave a half-written record at the end of an append-only file, and a checksum is how a reader tells it from a whole one (DDIA L2471). DDIA's example detects such a record and ignores it. This rule is stricter, because the send waits until its journal entry is on stable storage. A torn record at the end of the journal is then an order that never went out, and reconciliation confirms that before trading resumes. A torn or failing record anywhere else is corruption, and the reader halts and alerts. Recorded data nobody reads is still read back on a schedule, its checksums verified and its copies compared, because data that is only checked when read can rot unseen (DDIA L5489, L\~16792). The read-back is an alarm, so a dead-man check covers it.
4. **A case the design calls impossible ends in a halt and an alert, never in a guess.** Real code still has to handle what an algorithm assumes cannot happen, even when the handling is to stop and leave the cleanup to a person (DDIA L9488). DDIA divides properties into safety, meaning nothing bad happens, which must hold in every case, and liveness, meaning something good eventually happens, which may wait on conditions (DDIA L9454, L9466, L9469). Here every hard limit is a safety property and trading is a liveness property. A design may give up trading to keep a hard limit, and never the reverse. A safety property holds within a stated model of what can go wrong, and DDIA calls a model that bounds every pause unrealistic (DDIA L9405, L9466), so no hard limit here depends on timing. A cancel reduces risk, so it is not trading under this rule. Every halt and the kill switch say what happens to orders still working at the broker. The kill switch can cancel them when the journal's tail is torn or the sender is gone, journaling its cancels in a new segment and sending them from the rate-limit share reserved for cancels.
5. **A value from outside the process is checked against a sane range and a size limit when it is parsed, and a value that fails halts its consumer.** DDIA recommends such checks even between services that trust each other (DDIA L9360). A negative price or an absurd quantity in a vendor or broker message stops the reader before it reaches a decision.

### Time comes from one clock, and order from sequence numbers

1. **Elapsed time is measured on a monotonic clock, and the journal orders its entries by a sequence number it assigns.** The time-of-day clock can jump backward when the time service resets it, and a paused virtual machine sees time jump forward (DDIA L8811, L8823, L8878). A counter orders events without measuring time, which DDIA calls the safer way to order them (DDIA L8966, L10533), when one assigner increments it. Counters kept by several nodes, or handed out in blocks, do not agree with the order events happened in (DDIA L10556). So each account's journal numbers its entries from one counter, the numbers have no gaps, a gap halts the reader, and numbers from two accounts are never compared, since order holds only within one partition (DDIA L10731, L6201). The shared clock offers both readings, every timeout reads the monotonic one, and a timestamp in the journal records when something happened, never in what order. A monotonic clock does not defend against a pause, which can fall between a check and the act it guards (DDIA L9084).
2. **The machine's offset from reference time is measured, and an offset past a set bound halts trading.** A computer's quartz clock drifts, a blocked time service can go unnoticed, and a time server can be wrong by hours (DDIA L8846, L8853, L8859). DDIA's rule for software that relies on synchronized clocks is to monitor the offset and take a node whose clock has drifted too far out of service (DDIA L8913). Here the clock sets session boundaries, data freshness and every captured timestamp, so its offset is one of the inputs hard limit 3 halts on. A time client that cannot reach its servers keeps reporting its last offset while the real error grows, so trading also halts when the last successful sync is older than a set age, and the offset is measured against several servers, since one can be wrong by hours (DDIA L8851, L9360). The bound comes from what slippage measurement needs. The 100-microsecond rule DDIA cites as a draft for high-frequency firms (DDIA L8887) is far tighter than a platform this slow needs.
3. **Captured data keeps the source's event time, the source's send time where the feed has one, and the local receive time side by side, and rate monitors window by event time.** Mixing event time with processing time makes a backlog processed after a restart look like a burst of activity (DDIA L14747). A clock outside the platform's control can be wrong, so DDIA logs three timestamps, the event and send times on the sender's clock and the receive time on the receiver's, and estimates the offset between the clocks from the send and receive times (DDIA L14784, L14788). None of them overwrites another. This extends the [charter's premise](team-charter.md#the-premise-what-must-not-fail) that data records when it arrived and when it became knowable, where receive time is when it arrived and event time is when it became knowable.
4. **A decision reads the time and random numbers only from the shared clock and a seed the journal records, and it depends on nothing else that can change between runs.** A replica that re-runs a statement calling the current time or a random number computes a different result (DDIA L4912), and a replay does the same. DDIA's full list adds iterating over a hash table and reading from an outside source (DDIA L13148). So no module calls the system clock or an unseeded random source directly, iterates a set or a dictionary keyed by strings where the order affects the result, or fetches from outside mid-decision. Each decision's journal entry also names the version of the reference data it used: risk limits, instrument metadata, configuration and the cost model. DDIA's version of that rule gives each version of a changing reference record its own identifier and joins against the version current at the time (DDIA L14943).
5. **Replay delivers events in the order live capture received them, and never re-sorts them by event time.** A node that must decide now cannot know which earlier-stamped event is still on its way, so ordering by timestamp finds the answer only after everything has arrived (DDIA L10603). A backtest that sorts a day by event time decides with hindsight no live run had. Whatever wait for late events the live loop applies, replay applies the same one, and replaying one day twice, from the same recording, gives the same decisions.

### Every fact has one writer

1. **Each fact has one authoritative store, and a copy of a value that changes is derived.** The book requires a single point of truth for any value copied across a system, updated in one place (AoS L8153). DDIA calls the two kinds a system of record and derived data, and where they disagree the system of record is right by definition (DDIA L11985). Here the journal records every intent, order, acknowledgement, fill and cancel when it happens, and the broker is the truth for holdings and cash at the moment the platform asks. The two are independent records that reconciliation compares and never overwrites, and a mismatch halts trading. Positions and cash held anywhere else are derived and rebuilt once the two agree. Captured data, every backup of it or of the journal, and every broker statement the platform saved are recorded facts, not derived copies.
2. **The quantity that sizes an order counts every order already sent.** The book asks three questions of any replicated read, and one of them decides this case: will the value feed a later write (AoS L7901)? Here the gate and the sizing both measure against the broker's holdings plus every order the journal shows as sent, working or unknown, each counted as filled or unfilled, whichever is worse for the limit being checked. A strategy's own position comes from the journal's fills, and reconciliation checks the strategies' sum against the account. Risk limits, instrument metadata and configuration may be cached with a maximum age. Their refresh, like every session boundary, reads the shared clock rather than the wall clock, so a backtest refreshes the same way live trading does.
3. **One process sends for an account, and an order with no answer blocks the next.** State that must survive a restart is rebuilt from the journal and the broker, and a rebuild that cannot read either leaves the platform halted. The book's order of preference is to avoid state, then to move it out of the process (AoS L8393, L8827). Only the process holding the account's lease writes the journal or sends to the broker, and a standby takes the lease only after the old one has expired or been revoked, then reconciles before it sends. The send waits until its journal entry is on stable storage, through `fsync` or the store's equivalent, since durability means waiting for the write before acting on it (DDIA L\~6894). DDIA adds that no single technique makes a write durable, so the journal also keeps a second copy and old backup generations (DDIA L\~6930). The book never names `fsync`, and choosing it is this platform's reading. Each journal entry carries a client order id fixed by the decision before the send, the broker receives the same id, and a resend reuses it unchanged, including a resend by a later holder. A resend is safe only where the broker rejects a client order id it has already seen, so the broker adapter states whether its broker does and for how long, and a test on the paper account shows it. Against a broker that does not, an unknown order is looked up by its id and never resent. An order the broker never acknowledged is unknown rather than failed. It blocks every further order on its account and instrument until reconciliation settles it, and if it stays unknown past a set time, trading halts and the owner is alerted. The simulated broker can withhold an acknowledgement, so replay runs this path. These rules go beyond the book, which discards a timed-out call (AoS L8698). DDIA's reason for treating the order as unknown is that a request that timed out may have landed with only its response lost, so a retry repeats it unless the receiver drops duplicates (DDIA L4204, L4207).
4. **At 1x the single sender is a lock the operating system releases only when its holder exits, and the send to the broker is not fenced.** A process can pause at any point, past the end of a lease that expires on a timer, in a garbage-collection pause, a suspended virtual machine, swapping or a blocking disk write, and wake up acting as if it still held the lease (DDIA L9084, L9094, L9102, L9110). DDIA's answer is a fencing token: each grant carries a number higher than every earlier grant, and the protected resource itself refuses a write carrying a lower number than one it has seen, since a client checking its own lease is not enough (DDIA L9274, L9286). For a resource that does not check tokens it suggests working the token into what the resource stores (DDIA L9292). The broker does neither, and the book offers nothing for that case, so nothing fences the send, and this design does not claim to. At 1x one machine holds the lock, and the operating system releases it only when the holding process exits, so a paused holder keeps it and a second sender cannot start. Every journal entry and every client order id still carries a lease number from the first commit, because the journal is never migrated and a field added later would create a second format. When a lease that expires on a timer arrives, such as a standby on a second machine, four mechanisms are built with it.
   1. The journal refuses a lease number below the highest it has accepted, in the same atomic step as the append, and a new holder's first act is a journal entry carrying its number.
   2. A new lease number exceeds every lease number in the journal and in the client order ids the broker reports for the account, so a restore from backup cannot wind it back. DDIA's case of a reused number is a promoted replica whose lagging counter reissued keys another store already held, and showed private data to the wrong users (DDIA L4868).
   3. An order journaled under an older lease stays counted, and keeps blocking its instrument, until the broker reports it or the old process is confirmed gone. A new holder never settles it as unsent because the broker shows no record of it.
   4. Reconciliation flags any broker order whose client order id carries an older lease number and that arrived after a takeover, and halts.

   A test pauses one holder between its journal write and its send, lets a second take over, resumes the first, and asserts that the broker holds one order or that the platform has halted.
5. **Each fill applies once, keyed by the broker's execution id, and every decision that reads shared buying power runs in the account's one sender, one at a time.** Only an id carried from end to end can drop a duplicate, because each layer below sees only its own retries (DDIA L16438). The duplicate check is a uniqueness constraint in the journal's store, in the same step as the append, because a check for a row that does not yet exist has nothing to lock, and two inserts can each pass it (DDIA L7635). Reconciliation journals a fill it fetches from the broker under that fill's execution id, so a late copy from the stream is then dropped. A broker's correction or bust of a fill is a new entry that names the execution it replaces, as a ledger adds a compensating entry rather than editing the old one (DDIA L\~14416), and the derived position applies the latest version of each execution once. Every update to derived state sets a value or is keyed by an id that drops a repeat, since an increment applied twice counts twice (DDIA L\~14993). Two strategies that each read the account's buying power and then order against it can each pass the check and together exceed it, the race DDIA calls write skew (DDIA L7538). Its remedy without a transaction is to send every write that might conflict to one partition and process them in order (DDIA L16535), and it finds that one thread in a loop "can sometimes perform better" than concurrent execution by skipping the cost of locks (DDIA L7725). That is the one sender per account, deciding in sequence. DDIA's limits for it are that each decision is short and fits in memory with no network wait inside it (DDIA L7821), and the sender re-reads the halt state just before each send. The remedy covers only writes through the sender. The owner's own trades at the broker, and anything the broker does to the account, show up only when the gate reads the broker's buying power, so it reads it fresh before each order.

### Recorded data is append-only, and every view of it is rebuilt

1. **Recorded data is never updated or deleted in place, and a correction is a new record.** Append-only files make crash recovery and concurrency simpler, because a crash cannot leave a value half overwritten (DDIA L2484). The engines DDIA describes are append-only on the way in, yet they compact segments by key, keeping only the latest value for each key and dropping the rest (DDIA L2437). So recorded data never sits in a store that compacts by key, unless every record has a key of its own. DDIA's event sourcing records each action's intent in neutral terms rather than the side effects it had, so a later feature can derive new effects from old events (DDIA L14319). Here the journal records what a strategy asked for as well as the orders that followed, and a cancel or a correction is a new entry that points at the old one. A test rebuilds positions from the journal and compares them with the running state.
2. **A new read view is built from the same record and runs beside the old one, rather than migrating the record.** Separating the form data is written in from the forms it is read in lets a new view run alongside the existing ones, and the old one is shut down once nothing reads it (DDIA L14461, L14470). This is how a stored format changes under the two-release rule below: derived tables move, and captured data and the journal stay as written.
3. **Recorded formats are language-neutral and versioned, and nothing recorded or read from outside is a pickle.** A language's built-in serialization ties the data to that language, tends to neglect versioning, and lets whoever controls the bytes run code when they are decoded (DDIA L3623, L3626, L3632). So every recorded record names the schema it was written with, a registry keeps every schema ever used, and Python's `pickle` never touches captured data, the journal, or anything that arrives from outside the process. Readers keep reading every schema ever written, under the two-release rule below. Data outlives code, so a record written today is read by code that does not exist yet, and a rollback has older code read newer records (DDIA L\~3874, L\~4104). A release passes a compatibility check against every schema in the registry: a field is added only with a default, an identifier is never reused, and a field is removed only if it had a default (DDIA L\~3973). A step that reads a record and writes one back keeps the fields it does not understand, or it drops them silently (DDIA L\~4071, L4319). Prices, quantities and identifiers never pass through a float, since a JSON parser that reads numbers as floats corrupts integers above 2^53 (DDIA L3632).
4. **Captured data is stored as received, and parsing it into the platform's model is a derived step that can run again.** DDIA finds that making raw data available quickly is often worth more than settling the ideal model first, and leaves its interpretation to the reader (DDIA L12909, L12920). This doc adds its own reason: a parser bug then costs a rerun rather than a lost day.
5. **A backup copies closed segments, names the journal position it is consistent with, and leaves the machine before the first capture is relied on.** A copy taken while writes continue holds parts from different moments, and restoring it makes the mismatch permanent (DDIA L7227). DDIA's segments are never modified once written (DDIA L2449), and this doc infers that a closed segment gives the backup a consistent point to copy. A new copy of a store is a snapshot tied to an exact log position, then every change after that position (DDIA L4777), so each backup records the journal position it covers. A machine in the cloud can vanish without warning (DDIA L293), so a copy of captured data and the journal exists off the machine from the first session on. A restore drill checks record counts, checksums and the lease numbers the restored journal holds.
6. **A batch output is written whole to a new place and switched to in one step, and the old output stays until the new one is checked.** DDIA's example loads new files beside the old ones, switches over atomically and can switch back, since the old files are still there (DDIA L12811, L12822). Here that covers backtest results, feature tables and any derived store the loop reads. A multi-part output becomes visible through one small completion record written last, naming the parts, counts and checksums it covers, the way a single node commits when its commit record reaches the disk (DDIA L10857). A reader treats an output with no completion record as missing, which halts under hard limit 3, never as empty. Inputs are read-only, so a run can repeat without harm (DDIA L12311). A job also writes nothing outside its output and reads reference data only from a snapshot placed beside its inputs, because a query to a live store mid-run makes the job slow and its result depend on when it ran (DDIA L12545). Regenerable then means identical on a second run, which a test checks by building each derived artifact twice and comparing checksums (DDIA L13148).
7. **Derived state changes only by consuming the journal in order, and stores the journal position it reflects.** Two writers updating two stores can land in opposite orders with no error, leaving the stores different for good, so no component writes to both the journal and a view of it (DDIA L\~14160). Once an entry is in the journal it is a fact, and no component downstream may reject it. A check runs before the append, or its verdict is a later entry of its own (DDIA L14372). Each derived store saves the journal position it reflects in the same write as the value, so a restore from a snapshot plus the journal's tail equals a full replay, and a test crashes between the apply and the save to show it (DDIA L\~15043).

### Coordinate only where a mistake cannot be undone

1. **The order path coordinates, and everything else is asynchronous and may lag.** DDIA separates timeliness, meaning the reader sees the latest state, from integrity, meaning no state is ever wrong. A lapse in timeliness heals on its own and a lapse in integrity stays (DDIA L16612, L16626). Many businesses accept a briefly broken constraint and apologize for it, and paying for coordination only where it is needed buys speed and availability everywhere else (DDIA L16676, L16700, L16711). An order cannot be taken back, so the risk gate and the sizing coordinate through the one sender, while monitoring, reports and research may lag. A lagging view is late and still right only while delivery is reliable, ordered and free of duplicates. A view that misses one message is wrong for good (DDIA L\~16028), which the gap checks above catch. DDIA also leaves the size of a tolerated breach to the business, and notes that coordination trades fewer apologies for inconsistency against more for outages (DDIA L16676, L16693). Here a halt is the outage, and its price is missed trading. This is the reasoning behind the isolation rules above, seen from the data's side.
2. **No transaction spans the journal and the broker, and no consensus algorithm is written here.** Two-phase commit needs every participant to answer, so it spreads one part's failure to all of them, and its coordinator becomes a database whose loss leaves locks held until someone intervenes (DDIA L11110, L11150, L11174). A broker could not take part in one anyway. The journal before the send, a client order id carried end to end and reconciliation reach the same result without one, which is the log-based approach DDIA describes for a transfer between two accounts (DDIA L16554, L16636). The journal, the id and reconciliation reach that result only where the broker rejects a repeated client order id, which the one-writer rules above require the broker adapter to show. DDIA lists the problems that all reduce to agreement among nodes, among them a lock or lease, a uniqueness constraint, a counter with no gaps and an atomic commit (DDIA L\~11482). Here those are the sending lease, the journal's sequence, client order id uniqueness and the block on unknown orders. At 1x they all sit on one machine. If one must survive the loss of that machine, all of them move together to an existing coordination service, since DDIA advises against implementing consensus oneself (DDIA L11247, L11519). DDIA names three ways a single decider can fail over: wait for it, fail over by hand, or fail over automatically (DDIA L11519). The sender's lease waits or fails over by hand. The owner is a single decider too, and when the owner cannot be reached the platform stays halted or on paper.

### Every change can be undone or switched off

1. **A strategy can be switched off without a deploy.** The book's rule is to design anything released so it can be turned off, which is faster than a rollback and leaves the rest of the release running (AoS L4800, L6358, L6996). Here the switch is a per-strategy halt that leaves the other strategies trading. Like every halt under hard limit 3, it stops new orders and never reads as a target of zero. Switching a strategy off is anyone's to do, while switching it back on in live trading is the owner's, on the owner's ruling of 2026-11-02.
2. **A change to a stored format ships in two releases: the code first, the data later.** Old fields and tables stay for as long as a rollback may need them (AoS L6327, L6335). The book puts the price of rollback at under 1% of a release for most changes, and finds the large releases that skip it are the ones that need it most (AoS L6340, L6348). Captured data and the journal are never migrated. A new format applies to new writes, every reader keeps reading every format ever written, and a test replays a journal holding each of them.
3. **A release is compared with the one before it, and a sudden gain is a finding too.** A jump in throughput can mean a code path or a filter was dropped (AoS L5876). Replays of the same recorded day must match on their counters, such as orders, rejects and fills. Each timing carries a written tolerance in both directions, set from this platform's own run-to-run spread, and the book's worked example uses 5% (AoS L11260). Any change past those bounds without an intended cause goes to the builder (AoS L11226, L11254).

### Monitoring answers whether there is a problem first

1. **The first monitors answer "is there a problem", and there are between three and ten of them.** Monitoring built bottom-up from host metrics produces alerts that teams learn to ignore, and then a customer reports the outage first (AoS L10210, L10223, L10355). Here the first monitors are these nine.
   1. P&L against expectation.
   2. Exposure against limits.
   3. Fill and reject rates.
   4. Slippage against the cost model.
   5. Data freshness.
   6. Orders in an unknown state, and reconciliation mismatches.
   7. Capture-disk and journal headroom.
   8. Whether the platform is halted, and why.
   9. The heartbeat.

   "Where is the problem" and "what is the problem" come after, in that order (AoS L10335).
2. **Every halt is a fixed rule, and statistics only escalate.** The book alerts when a value leaves several standard deviations of its own history at the same time on similar days (AoS L10168, L10313). Here that applies only to counters that behave like rates, such as fills, rejects and message rate, and only after the baseline holds a stated number of sessions. Until then a fixed threshold stands in, and the statistical alert is drilled on recorded history. A limit breach, the loss stop, a reconciliation mismatch and missing or stale input each halt by a fixed rule, because hard limit 3 cannot wait for a statistic.
3. **Latency is recorded as histograms and reported as percentiles, and histograms combine by adding.** A mean hides how many requests saw a delay, the slow tail is where the busiest accounts tend to sit, and averaging percentiles from several sources is meaningless (DDIA L518, L523, L536, L583). A request that waits on several calls is as slow as the slowest of them, so the tail grows with every call added (DDIA L569). So every latency monitor and every timing in the release comparison is a percentile, such as the median and the 99th, read from merged histograms. A load test sends on its schedule whether or not the last reply has come back, since a harness that waits for each reply keeps its queues artificially short (DDIA L551). Order latency is timed at the broker adapter, where the waiting the caller sees is.
4. **Every queue and buffer states its bound, in time as well as size, and what it does when full, and capture never discards data to stay inside its bound.** A backlog can grow unseen until the disk fills, as when compaction falls behind the writes with nothing to slow them (DDIA L2766). A full queue can drop, buffer or push back on its sender (DDIA L13767). A vendor feed cannot be pushed back on, so capture buffers and spills to disk, and dropping is allowed only for a value a later one replaces, with every drop counted. A log kept in a fixed-size ring drops its oldest entries when it fills (DDIA L14037), which for captured data is loss. How far a consumer trails the head of a log is the number to alarm on (DDIA L14056). Here that lag is measured on the capture buffer and the journal writer, and reports under the first monitors' data freshness and headroom, so the list stays at nine. The capture disk alarms at 75% of its limit under rules 2 and 4 of the first section. The journal's disk is on the order path, so it halts trading at its limit.

### Data has a cost, except the data that cannot be recaptured

1. **Every class of derived data has an owner and an end date.** Data costs more than its storage, and the book lists six costs that grow with it (AoS L8947). Most of its value falls with age, so keeping it forever needs a stated value and a time limit (AoS L8963, L9168). Diagnostic logs, intermediate backtest output and feature tables follow that rule. Derived data is rebuilt by a command rather than repaired by hand, since DDIA counts tools that recompute data among the ways to recover from human error (DDIA L391). Recorded data is exempt as a class: captured data, the journal, every backup of either, and every broker statement the platform saved. No lifecycle or cleanup rule may match a path that holds it. The operator's change log and incident evidence are kept as long as the operator sets on purpose, rather than by this rule. A legal duty to delete, such as a vendor's license terms, is the one exception, and it is a written procedure the owner carries out by hand, naming every copy it must reach, never a rule that runs on its own. DDIA notes that immutable stores and backups make deletion hard, and that collected data is a hazard to keep only while it is used (DDIA L\~14509, L17128).

### Buy what does not set the venture apart

1. **A component is built here only when it passes the book's four questions.** Does it set the venture apart from competitors? Is this team the best owner of it? How soon would a competitor catch up? Can it be built and supported for less than buying (AoS L5500)? The book finds it "not uncommon" to underestimate support cost by an order of magnitude for infrastructure that runs around the clock (AoS L5320). Here support lands on the owner's hours, so a build is priced in operator hours a year, not in tokens. The four answers and that price go on the issue, and the call is the owner's. The charter's build-or-buy note names the alpha models and the research platform as what the team builds. A bought component inside the loop runs in process, through the same interface, in every environment. One that runs only at the broker sits behind the broker adapter, and its simulated stand-in is named as a gap in the model.
2. **A vendor's own features sit behind the adapter at its edge, with an issue to retire them.** Deep integration with one provider raises the cost of leaving it (AoS L6727). When a crisis forces one in, the book's rule is to wrap it and commit to removing it (AoS L6794).

The price of these rules is that every path carries its mechanisms from its first run, and a design names its next split before any code needs it. DDIA's rules add a checksum, a schema identifier and a second timestamp to every recorded record, a sequence number and a lease number to every journal entry, a wait for stable storage before every send, a seed and a reference-data version to every decision, a copy off the machine and a scheduled read-back of everything recorded, and histograms in place of averages. What they buy is that load reaching 100 times the first takes configuration and more machines rather than a rewrite, which is what the owner's directive asks.

## How work is cut and ordered

A slice is the smallest set of deliverables that leaves the product usable by
someone at the end of it. Not a layer, and not a subsystem. A slice that ends
with a component nobody can run is a slice cut the wrong way.

Each slice lives on the tracker as three things.

1. A milestone with the slice's name, so a filed issue has one to take.
2. A parent issue holding what the slice leaves usable and the tests that show
   it works, each stated as what a test executes rather than what the code
   looks like.
3. One sub-issue per deliverable.

A sub-issue that cannot start until another finishes gets a "blocked by" link
to it, and a slice's parent issue that waits on another slice gets one to that
slice's parent issue. Name only the dependencies that are real. An invented
dependency is how a plan quietly becomes a layered build.

Order the slices by what the ranking rule in [CLAUDE.md](../CLAUDE.md)
decides: what is missing from the shortest path to a product someone can use
goes first. Then ship it, use it, and let what breaks set the order after
that. Slice 1 is the walking skeleton, on [#4](https://github.com/l3a0/ithildin-runtime/issues/4). The next slice is chosen
by what breaks while the skeleton runs on paper.

## Vocabulary

Terms with exact definitions, reused on purpose. A term listed here is not a
candidate for a synonym. Anything not listed here follows the writing-style
rule in [CLAUDE.md](../CLAUDE.md), which prefers deleting an in-group term to
glossing it.

| Term | Definition |
| --- | --- |
| **vintage** | One series as one source held it on one date, recorded with vendor, symbol, span, that date and which price the series carries, and kept unchanged once written. The term and its rules come from the sibling quantitative-trading repository |
| **target portfolio** | The positions portfolio construction asks for. The difference between it and the current positions is what execution trades |
| **risk gate** | The pre-trade check every order passes on the one order path. It enforces the risk engineer's limits and can refuse an order |
| **journal** | The append-only record of every intent, order, acknowledgment, fill, cancel and human override, written before the action it records |
| **order path** | The path from the target portfolio through the risk gate and the journal to the broker adapter. Its synchronous dependencies are the calls on it that leave the process or wait on input or output |
| **written scale limit** | The most load an implementation handles as built, stated beside the code that enforces it, as distinct from the most its design allows |
| **lease number** | The number each grant of an account's sending lease carries, higher than every earlier grant, recorded in every journal entry and client order id. Once a lease can expire on a timer, the journal refuses a write whose lease number is below the highest it has accepted |
| **event time** | When the source says an event happened, as the source's own timestamp states it |
| **receive time** | When capture received a record, read from the shared clock |
| **walking skeleton** | A build in which every module exists in its simplest form and the whole loop runs end to end |
| **exploratory** | A result found by looking at the data. It kills an idea or justifies a closer look, and is never a verdict |
| **registered** | A result whose hypothesis was committed in writing before the number was seen. Only a registered result can promote a strategy |

## Configuration

Machine-local config lives under `~/.config/ithildin-runtime/`. Nothing
tracked in this repository carries a secret or a machine-specific path.

No setting exists yet. The first broker or data-vendor credential gets a row
here in the change that first reads it, naming where it lives and what reads
it. A credential lives in the environment of the run or in the machine's
keychain, and never in a file. The table takes the columns Setting, Secret,
Lives in and Read by.

## Considered and rejected

Machinery that was considered and cut, pinned here with the reason. The point
is that a decision stays decided. When something new is cut, add it here in
the same change that cuts it.

Reviews armor what exists and rarely ask whether it should exist, so this
register is also where the answer to "why is this needed" gets written down
once rather than re-argued.
